# SEO / GEO стратегия boonts.com

Версия: 5 сентября 2026. Горизонт: 90 дней после выпуска изменений. Статус: технический фундамент, статья RU/EN, редакционная правка и измерения реализованы. Фактический статус выпуска и проверок — в IMPLEMENTATION_REPORT.md; бизнес-эффект требует последующих наблюдений.

Краткий итог выполненной работы: [IMPLEMENTATION_REPORT.md](seo/IMPLEMENTATION_REPORT.md).

## 1. Решение и цель

Строить узнаваемость Roman Babunts / Роман Бабунц через проверяемые продуктовые решения и результаты. Основной результат сайта — квалифицированный разговор с человеком, которому нужен продуктовый лидер. Органический трафик и цитирования в AI-поиске — промежуточные показатели.

Подтверждено владельцем: **найм и консалтинг имеют равный приоритет**. Для каждого направления — отдельная кнопка календаря, событие и квалификация обращения. SheSafe — отдельный продукт и отдельная воронка; установки не суммировать с лидами персонального бренда.

Самое рискованное допущение исходного плана: читатель, ищущий известного эксперта, готов рассматривать автора обзора на роль продуктового лидера. Совместное упоминание имён этого не доказывает. Проверка: одна качественная подборка → переход к доказательному кейсу / профилю → квалифицированное обращение. До появления такого сигнала не масштабировать страницы «Roman vs [имя]».

**Приоритет инвестиций:** доказательства опыта → полезный материал под конкретное решение читателя → измеримость → расширение контента. Базовые технические ошибки исправляются до масштабирования. Гарантий ТОП-10, Knowledge Panel или цитирования LLM нет.

| Статья для каждого набора популярных имён | Пересекающиеся намерения и риск однотипного контента | Один URL на самостоятельное намерение в каждом языке; список экспертов оставить навигационным материалом |

## 4. Поисковые намерения и архитектура

Ниже — гипотезы запросов, не семантическое ядро с частотностью. Приоритет подтвердить по GSC и целевым рынкам. RU — языковая версия, а не автоматическое обозначение России; EN — не автоматическое обозначение США.

| Намерение | Примеры запросов | Страница | Польза и следующий шаг |
|---|---|---|---|
| Проверить человека после рекомендации | Roman Babunts, Roman Babuntc, Роман Бабунц | `/` | Профиль → опыт / источник → контакт |
| Оценить компетенцию кандидата | growth product manager portfolio, кейс продакт менеджера монетизация | Будущий доказательный кейс | Решение, вклад и результат → профиль / разговор |
| Выбрать чтение по продукту | product management experts to follow, кого читать продакт менеджеру | Существующий `roman-vs-experts.html` в RU/EN | Подборка по задаче → источник → тематическая статья |
| Спланировать Discovery при падении удержания | quantitative vs qualitative product discovery, кого интервьюировать при падении retention | Готовая `/insights/{lang}/data-and-interviews.html` | Диагностика и отбор респондентов → шаблон / кейс |
| Проверить экономику перед масштабированием | cohort LTV vs average LTV, как считать LTV по когортам | Будущая `/insights/{lang}/cohort-unit-economics.html` | Формулы, период, ограничения → пример / контакт |
| Оценить результат эксперимента | incremental revenue A/B test, как посчитать эффект A/B теста на выручку | Будущая `/insights/{lang}/incremental-revenue-experiment.html` | Проверяемый расчёт → доказательный кейс |
| Найти приложение SheSafe | SheSafe, SheSafe location sharing | `/shesafe/` и локализации | Функции и ограничения → App Store |

**Сохраняем существующие URL.** Смена `.html` на красивые адреса без подтверждённой необходимости добавит миграционный риск; GitHub Pages не исполняет произвольные серверные правила `_redirects` / `_headers`. Будущие адреса выше не включены в sitemap и hreflang до появления готовых страниц.

Перелинковка: главная → Insights → тематическая статья → связанный кейс → профиль / контакт. У каждой новой статьи минимум одна входящая контекстная ссылка из хаба и одна релевантная связь с другим материалом. Не добавлять ссылки на ещё не существующие статьи. SheSafe связывать с автором как с создателем продукта, не смешивать запросы личной безопасности с продуктовыми методологиями.

**Языки:** отдельный статический URL, собственный canonical, корректный `html lang`, ссылки возврата и переключатель языка. `x-default` — выбранная версия по умолчанию. Перевод должен отвечать тому же намерению, но не обязан копировать все примеры. Неполный перевод не включать в языковую группу. [Google: localized versions и hreflang](https://developers.google.com/search/docs/specialty/international/localized-versions)

**Конкурентный ориентир:** SVPG и Product Talk полезны как образцы ясного определения метода и первоисточника; это не автоматически прямые конкуренты за найм Романа. Обзор публичного поиска выявил [профиль Roman Babunts в LinkedIn](https://rs.linkedin.com/in/oempolice) и материалы по количественному Discovery. Такой результат не измеряет позицию boonts.com в Google/Яндексе. Полный конкурентный этап: по каждому из трёх тематических кластеров зафиксировать 5 результатов в выбранной стране/языке, тип страницы, решаемую задачу, доказательства, дату и пробел. Не оценивать «Domain Authority» без данных провайдера.

## 5. Доказательства и идентичность автора

Единый идентификатор автора: `https://boonts.com/#person`. Имена Roman Babunts, Roman Babuntc и Роман Бабунц относятся к одной персоне. `sameAs` — только реальные профили этой персоны; ссылки на экспертов туда не добавлять. `about` / `mentions` описывают содержание, не сотрудничество, рекомендацию или профессиональное равенство.

Реестр проблемных утверждений: [CLAIMS_REVIEW.csv](seo/CLAIMS_REVIEW.csv). Наличие фразы на собственном сайте — источник заявления автора, но не независимое подтверждение. `llms.txt`, JSON-LD и перевод не являются новыми независимыми источниками того же факта.

Для каждого кейса собрать: контекст и период; роль и зона ответственности; исходный показатель; вмешательство; метод оценки; результат; ограничения; разрешённый к публикации артефакт / внешний источник. Отдельно указать, где результат команды, где личный вклад. Различать выручку продукта, ARR, инкрементальный эффект и экономию. Не суммировать пересекающиеся эффекты.

Пока нет подтверждений, не распространять $100M+ на новые статьи и внешние профили. В существующих материалах требуется единое, согласованное с Романом определение этой цифры. Если доказать её невозможно, заменить на конкретное подтверждаемое описание ответственности. Не придумывать личные истории, даты, цитаты и testimonials.

Внешний авторитет: начать с уже опубликованных материалов Романа и корректности авторства / ссылок на профиль. Затем предлагать редакциям только кейсы с самостоятельной ценностью. Контакты с редакциями и публикации от имени автора — отдельное действие; в рамках этой работы сообщения не отправлялись.

## 6. Контент: три задания вместо серии сравнений имён

Рабочая очередь: один материал за раз, сначала язык, на котором есть лучшие исходные данные. Перевод — после фактчекинга оригинала. Оценки времени ниже — плановые, не обещание.

### Материал A. Количественные данные и интервью в Product Discovery

- Намерение: выбрать следующий шаг исследования при падении удержания. Предлагаемый title RU: «Кого интервьюировать при падении retention: данные, сегменты и Discovery». EN: «Quantitative vs qualitative product discovery: choosing whom to interview».
- Структура: короткий ответ → качество телеметрии → различие когорты и сегмента → выбор респондентов → альтернативные объяснения → эксперимент → ограничения. AJTBD, OST и продуктовые риски сравнивать по уровню решения; не объявлять один метод заменой остальных.
- Оригинальный вклад: таблица «сигнал → возможные объяснения → данные против гипотезы → респонденты → следующий тест». Пример должен быть либо подтверждённым кейсом, либо явно учебным сценарием.
- Критический пример: падение D14 retention может объясняться новым составом трафика или пропавшим событием, а не ухудшением продукта. До интервью проверить определения когорт и полноту событий; затем сопоставить клиентов с одинаковым контекстом.
- Первоисточники: канон AJTBD, Product Talk, SVPG [AJTBD: канон автора](https://github.com/zamesin/Next-Move-Theory-Canon-and-Skills/blob/main/Next-Move-Theory-Canon/Advanced-Jobs-To-Be-Done/ajtbd-key-theses.md); [Teresa Torres: getting started with discovery](https://www.producttalk.org/getting-started-with-discovery/); [Marty Cagan: the four big risks](https://www.svpg.com/four-big-risks/). Не приписывать автору метода выдуманную цитату или обязательное число интервью.
- Готовность: автор проверил свой опыт; есть источники у объяснений; читатель может выбрать исследовательский шаг; нет пересказа текущей подборки. Оценка: 1–2 дня редактора + 30–60 минут автора.

### Материал B. Когортная экономика перед масштабированием

- Намерение: понять, окупается ли привлечение в конкретном сегменте. Title RU: «Когортный LTV: что проверить до масштабирования привлечения».
- Структура: единица анализа и горизонт → определения CAC и маржинального LTV → зрелость когорт → observed vs forecast → sensitivity → решение.
- Оригинальный вклад: воспроизводимая таблица с исходными числами, формулами и диапазонами. На учебных данных обязательно подпись «иллюстрация, не данные Yandex / Semrush».
- Сложные места: валовая выручка не равна маржинальному доходу; blend CAC скрывает каналы; короткая когорта не подтверждает lifetime; сравнение paid и organic без правил распределения затрат вводит в заблуждение.
- Готовность: все определения, периоды и формулы воспроизводимы; автор подтвердил бизнес-контекст; нет универсального «LTV/CAC > 3 значит масштабировать». Оценка: 2–3 дня с проверкой модели.

### Материал C. Инкрементальная выручка эксперимента

- Намерение: отличить эффект решения от выручки всего продукта. Title EN: «Incremental revenue in an A/B test: attribution, uncertainty and limits».
- Структура: решение → контроль и распределение → метрика на единицу рандомизации → окно наблюдения → неопределённость → guardrails → допустимая экстраполяция.
- Оригинальный вклад: один разрешённый кейс или воспроизводимый учебный разбор; показать, что результат мог бы опровергнуть гипотезу.
- Сложные места: проценты и процентные пункты; анализ только платящих после изменения конверсии; сезонность; повторные просмотры результатов; перенос короткого эффекта на год; двойной учёт инкремента.
- Готовность: проверка расчёта, единиц и ограничений; разделение командного результата и личного вклада. Оценка: 2–4 дня после получения данных.

**Общий редакционный стандарт:** один ответ на одно намерение; понятный вывод в начале; источники рядом с утверждениями; таблица или артефакт по необходимости; дата изменения только при реальном обновлении; полезный следующий шаг. Количество слов, процент уникальности и оценка AI-детектора не служат критериями качества.

## 7. GEO без недоказанных обещаний

Google AI Overviews / AI Mode опираются на обычные требования Search. Доступность, индексируемость, текст и соответствующая ему разметка нужны; специальный AI-файл или новая schema не гарантируют показов. Google прямо уточнил, что `llms.txt` не повышает и не понижает видимость в Search. Поэтому поддерживаем его автоматически с малой стоимостью, а не как отдельный канал роста. [Google: AI features and your website](https://developers.google.com/search/docs/appearance/ai-features); [Google: changelog, FAQ 7 мая и llms.txt 15 июня 2026](https://developers.google.com/search/updates)

Разделять управление роботами: OAI-SearchBot — поиск OpenAI, GPTBot — обучение; у Anthropic поисковый Claude-SearchBot отличается от ClaudeBot. Google Search и его AI-функции не следует отождествлять с Google-Extended. Существующая политика разрешения обучения сохранена; её изменение — отдельное предпочтение владельца. Доступ по robots не обходит блокировку на CDN. [Google: AI features and your website](https://developers.google.com/search/docs/appearance/ai-features); [OpenAI: crawler roles](https://developers.openai.com/api/docs/bots); [Anthropic: crawlers and controls](https://support.claude.com/en/articles/8896518-does-anthropic-crawl-data-from-the-web-and-how-can-site-owners-block-the-crawler)

FAQ сохраняется как полезный формат вопросов и ответов; его JSON-LD должен совпадать с видимым текстом. FAQ rich results Google отключены с 7 мая 2026 — никаких обещаний дополнительного места в выдаче. Подтверждённого причинного эффекта FAQPage на LLM-цитирование здесь нет. [Google: changelog, FAQ 7 мая и llms.txt 15 июня 2026](https://developers.google.com/search/updates)

**Эксперимент с AI-видимостью:** фиксированный набор [GEO_PROMPTS.csv](seo/GEO_PROMPTS.csv), отдельные брендовые и небрендовые вопросы. В каждом сервисе 3 независимых новых диалога на вопрос раз в 4 недели. Фиксировать сервис/модель, дату, язык, доступность web search, точный вопрос, ответ, упомянутое имя, URL цитаты и фактическую корректность. Успешный ответ — не просто имя, а корректное утверждение с релевантным источником. Повторные ответы не считать независимыми пользователями или статистикой рынка.

Baseline пока не снят. Ни запросы к web-search tool, ни HTTP-запросы с User-Agent бота не заменяют этот эксперимент. AI-referral отдельно измерять по доступному referrer; отсутствие referrer не доказывает отсутствие AI-перехода.

## 8. Измерение и правила решений

| Показатель | Определение / источник | Baseline | Что делать по результату |
|---|---|---|---|
| Квалифицированные обращения | Уникальные реальные разговоры с релевантным запросом; ручной журнал, без личных данных в репозитории | Неизвестен | Главный показатель, фиксировать причину релевантности и источник со слов человека |
| Контактные действия | Клики календаря, email, LinkedIn; отдельно по landing page и каналу | Не проверен end-to-end | Это микроконверсии, не состоявшиеся звонки |
| Органический спрос | GSC: clicks/impressions/CTR по странице, запросу, стране и языку; бренд/небренд отдельно | Неизвестен | Сравнивать равные окна; не смешивать рост позиций со сменой состава запросов |
| Индексация | GSC / Яндекс Вебмастер: индексируемые URL, выбранные canonical, причины исключения | Неизвестен | 200 и sitemap не доказывают включения в индекс |
| AI-цитирование | Число ответов с корректной цитатой сайта / число выполненных фиксированных проб; отдельно по сервису | Не измерено | Диагностический эксперимент, не общий market share |
| Производительность | CrUX p75: LCP ≤2,5 с, INP ≤200 мс, CLS ≤0,1; mobile/desktop отдельно | Не измерена | При отсутствии CrUX использовать Lighthouse для диагностики, не выдавать его за полевые данные [web.dev: Web Vitals](https://web.dev/articles/vitals) |
| Техническая целостность | `npm run build` + `npm run test:seo` | 12 страниц; 12 регрессионных тестов | Ошибка блокирует загрузку сборки в Pages |

Первые 7 дней: определить рынки / приоритет найма или консультаций, снять доступный baseline GSC за 90 дней, проверить контактное событие от браузера до отчёта, начать журнал обращений. Не извлекать органические обращения из одного агрегата pageview.

Через 28 дней после публикации: проверить переобход, выбранный canonical и запросы страницы. Если URL не индексируется — сначала диагностика доступа / canonical / качества; публикация ещё 10 статей проблему не решает. Если есть показы по неверному намерению — менять постановку страницы. Если релевантные посещения есть, а переходов к профилю / контактам нет — проверить полезность следующего шага и соответствие аудитории.

Через 8–12 недель: расширять кластер при появлении релевантного спроса и качественных контактов. При малом объёме данных не объявлять отсутствие конверсий доказательством провала; продлить наблюдение или провести качественный разбор обращений. Численные бизнес-цели задать после baseline, а не обещать рост в процентах от неизвестного значения.

## 10. Правила сопровождения

1. Страницы редактировать в `src/**/*.html`; публичные служебные документы — в `public/`. `dist/` — результат сборки, в этом репозитории он уже версионируется.
2. Новый канонический URL зарегистрировать в `seo/pages.json`. Vite автоматически берёт оттуда исходные HTML. Страница должна существовать до регистрации hreflang-связей.
3. Менять видимый FAQ и его JSON-LD вместе. `datePublished` сохранять, `dateModified` обновлять по реальной редакционной правке; сборка не «освежает» даты автоматически. Для остальных страниц `lastmod` опущен, пока нет достоверного источника даты.
4. `npm run seo:generate` пересоздаёт `public/sitemap.xml`, `public/llms.txt`, `public/llms-full.txt`. Эти файлы не редактировать вручную.
5. `npm run build` проверяет исходники, собирает сайт и проверяет `dist`; `npm run test:seo` проверяет обнаружение повреждённых canonical, языков, FAQ, автора и других регрессий. Требуется Python 3.9+ наряду с Node.
6. После выпуска запустить `npm run seo:live`. Это HTTP/HTML-проверка, не Rich Results Test, не инспекция Googlebot и не отчёт CWV. Проверить заголовки, ответы, отсутствие блокировок и изменения CDN.
7. Plan и evidence теперь не исключены из Git. Сохранять их вместе с релевантными изменениями, без секретов, персональных лидов и закрытых исходных данных.
